## 1. 시스템 개요

### 1.1 목적

저장 및 불러오기 시스템은 플레이어의 영구 성장 정보와 획득한 보상을 게임 종료 및 재실행 이후에도 유지하도록 관리한다.

특히 던전 진행 중 획득한 보상, 던전 클리어 보상, 장비 및 스킬 정보가 의도치 않게 소실되거나 중복 지급되지 않도록 하는 것을 목표로 한다.

### 1.2 주요 기능

- 플레이어 영구 데이터 저장
- 게임 시작 및 재실행 시 저장 데이터 불러오기
- 돈과 경험치 보존
- 레벨 및 스탯 포인트 보존
- 획득 아이템·재료·장비 보존
- 보유 및 장착 스킬 보존
- 던전 클리어 보상 저장
- 중복 보상 지급 방지
- 던전 재시작과 영구 데이터 분리
- 개발용 저장 데이터 초기화

### 1.3 기존 구현 현황

저장 및 불러오기 기능은 구현 완료 보고가 존재한다.

사용자는 Unity Play를 중지한 뒤 다시 실행해도 경험치와 돈 등이 유지되는 것을 확인했다고 보고했다.

다만 이는 사용자 보고 기준이며, 전체 데이터 항목과 저장 구조를 직접 검증한 것은 아니다.

## 2. 저장 데이터의 구분

### 2.1 영구 데이터

영구 데이터는 던전 클리어·실패·재시작 또는 게임 종료 이후에도 유지해야 하는 정보이다.

주요 대상:

- 돈
- 경험치
- 레벨
- 획득한 제작 재료
- 획득한 아이템
- 보유 곡괭이
- 제작한 곡괭이
- 장착 장비
- 보유 스킬
- 장착 스킬
- 성장 능력치
- 미사용 스탯 포인트
- 사용한 스탯 포인트

실제 현재 저장 시스템이 이 항목 전체를 지원하는지는 Unity 프로젝트 확인이 필요하다.

### 2.2 런 내부 데이터

런 내부 데이터는 한 번의 던전 플레이 과정에서 관리하는 상태이다.

| 데이터 | 방 이동 시 |
|---|---|
| 현재 체력 | 유지 |
| 남은 물약 | 유지 |
| 남은 부활 횟수 | 유지 |
| 현재 던전 및 난이도 | 유지 |
| 런 획득 보상 기록 | 유지 |
| 전투 기록 | 유지 |
| 현재 방 진행 상태 | 진행에 따라 갱신 |

런 데이터는 방을 이동한다고 초기화되지 않는다.

### 2.3 런 데이터와 영구 저장 구분

**런 데이터를 방 사이에서 유지하는 것과, 게임 종료 후에도 저장하는 것은 서로 다른 개념이다.**

현재 체력, 물약, 남은 부활 횟수 및 현재 방 진행 상태를 게임 종료 이후에도 복원하는지에 대한 규칙은 확정되지 않았다.

따라서 진행 중인 던전의 중단·재개 기능이 존재한다고 단정하지 않는다.

### 2.4 보상 데이터와 런 기록

돈, 경험치, 아이템 등 실제로 획득한 데이터와 결과창에 표시하는 런 기록을 구분한다.

런 기록은 해당 플레이에서 무엇을 얼마나 획득했는지 표시하기 위한 정보이다.

결과창을 표시하기 위해 런 기록을 읽는 행위가 보상 재지급으로 연결되어서는 안 된다.

## 3. 돈 및 경험치 저장

### 3.1 돈

몬스터 처치 시 돈을 즉시 획득한다.

획득한 돈은 영구 유지 대상이다.

던전에 실패하더라도 이미 획득한 돈을 회수하지 않는다.

### 3.2 경험치

몬스터 처치 시 경험치를 즉시 획득한다.

획득 경험치는 플레이어 레벨과 연동한다.

던전에 실패해도 이미 획득한 경험치를 유지한다.

### 3.3 레벨

현재 플레이어 레벨은 영구 저장 대상이다.

던전 재시작 또는 실패를 이유로 레벨을 초기화하지 않는다.

### 3.4 클리어 돈·경험치

**확정 규칙**

별도의 던전 클리어 돈·경험치 보너스는 없다.

결과창에 표시되는 돈과 경험치는 해당 런에서 이미 획득한 데이터를 기준으로 한다.

결과창을 열 때 돈이나 경험치를 다시 지급하지 않는다.

### 3.5 구현 확인 사항

- 돈 저장 및 복원
- 경험치 저장 및 복원
- 레벨 저장 및 복원
- 처치 보상과 저장 데이터의 일치
- 결과창 재열기에 따른 중복 지급 여부

## 4. 아이템 및 재료 저장

### 4.1 획득 재료

일반 몬스터는 기존 확정 드롭 규칙에 따라 재료를 지급한다.

- 드롭 성공 확률: 50%
- 성공 시 수량: 1~2개

획득한 재료는 영구 보유 데이터에 반영한다.

### 4.2 아이템 데이터

저장 대상에는 획득한 아이템이 포함된다.

정확한 아이템 ID, 데이터 구조 및 수량 보관 방식은 현재 프로젝트 확인이 필요하다.

### 4.3 인벤토리와의 연동

저장 데이터를 불러온 뒤 보유 아이템과 재료가 인벤토리에 정상적으로 표시되어야 한다.

인벤토리를 열거나 닫는 것만으로 보유 데이터가 변경되어서는 안 된다.

### 4.4 던전 실패

던전 실패 시 이미 획득한 재료와 아이템은 100% 유지한다.

실패했다고 기존 획득 재료를 회수하지 않는다.

### 4.5 확인 필요 사항

- 아이템 종류별 저장 방식
- 수량 데이터 저장
- 동일 아이템 중첩 보관
- 아이템 ID 변경 시 기존 데이터 처리
- 보유 아이템과 UI 표시의 일치

이 항목은 현재 구현 검증 대상이며 새로운 저장 방식을 확정하지 않는다.

## 5. 장비 및 스킬 저장

### 5.1 곡괭이

저장 대상으로 관리해야 하는 정보:

- 보유 곡괭이
- 제작한 곡괭이
- 장착한 곡괭이

곡괭이 제작 기능은 아직 구현 완료 보고가 없다.

따라서 제작한 곡괭이의 저장 기능까지 완료되었다고 단정하지 않는다.

### 5.2 다른 장비

기존 인벤토리 기획에는 상의, 하의, 악세서리 슬롯이 포함되어 있다.

장비 및 성장 관련 데이터는 영구 유지 대상이지만, 확장 장비의 실제 콘텐츠와 저장 지원 상태는 확인이 필요하다.

### 5.3 스킬

저장 대상:

- 획득한 스킬
- 장착한 스킬

기존 플레이어 스킬 4종의 구현 완료 보고가 있다.

정확한 스킬 ID, 장착 슬롯 및 저장 데이터 구조는 확인이 필요하다.

### 5.4 장착 상태 복원

저장한 장비와 스킬의 장착 상태는 불러오기 이후에도 유지되어야 한다.

장착 정보와 실제 전투에서 사용되는 장비·스킬이 일치하는지 검증한다.

### 5.5 제작 데이터 연동

향후 곡괭이 제작 기능이 구현되면 제작 과정의 돈·재료 사용과 곡괭이 획득 결과가 영구 데이터에 올바르게 반영되어야 한다.

구체적인 저장 시점과 방식은 제작 기능의 상세 구현을 확인하여 정한다.

## 6. 스탯·성장 저장과 기존 캐릭터 이전

**2026-10-23 최신 사용자 승인 반영.** 승인 기획과 [WORK_STATUS.md](../WORK_STATUS.md)의 Codex 구현·검증 보고를 구분한다. 이번 작업은 문서 갱신과 관련 코드의 읽기 전용 확인이며 Unity 컴파일·Play·빌드 검증은 재실행하지 않았다. 아래 과거 구현 기록은 당시 이력으로 보존한다.

### 6.1 영구 성장 대상과 신규 규칙

경험치·현재 레벨·미사용P·사용한P·체력/물리/마법 투자 결과와 영구 성장 정보를 관리한다. 신규 승인은 Lv.1 초기3P·레벨업3P·최대Lv.50/총150P, 스탯별100P 상한과 자동 패시브 해금이다. 기존1P 지급 기획은 대체한다. 기존 재화·재료·보유 및 장착 스킬·설정 등 영구 정보는 보존한다.

투자 [+]는 클릭 즉시 투자·저장을 요청하는 기획이다. 포인트 소모·투자 결과·표시가 일치해야 하며 메인 전용 골드 스탯 초기화도 기존 영구정보를 전체 초기화하는 기능이 아니다. 던전 입장 시 구성 고정/투자 금지와 기존 방 이동 자원 유지·실패 보유 유지 규칙을 보존한다.

### 6.2 개편 이전의 사용자 제공 Codex 읽기 전용 조사 (과거 기록)

2026-10-22 개편 전에 사용자가 제공한 읽기 전용 분석을 보존한다. 아래 v1 내용은 당시 조사 결과이며, 이번 확인한 현행 코드는 §6.4/6.6과 구분한다.

- 당시 CharacterSnapshot은 version1이며 레벨·경험치·미사용 포인트를 저장한다.
- 스탯별 투자량과 이전 완료 플래그는 없다.
- 당시 읽기는 version1만 허용했다.
- .tmp 쓰기 및 .bak 복구 구조를 사용한다.
- 과거 Lv.5에서 버려진 경험치는 복구할 수 없다.

기존 WORK_STATUS의 저장 구현·검증 보고와 위 읽기 전용 조사를 구분한다. 이 조사는 개편 이전 상태이며 현행 v3 지원 여부는 아래 최신 구현 기록을 따른다.

### 6.3 확정된 포인트 이전 원칙 — 현행 v3 구현 보고와 구분

기존 캐릭터의 **레벨과 현재 레벨 진행 경험치**를 유지한다. 기존 투자 결과가 있다면 유지한다.

`해당 레벨 총 획득 포인트 = 현재 레벨 × 3P`

`보정 후 미사용 포인트 = 해당 레벨 총 획득 포인트 - 기존 투자 포인트`

정상 기존 v1 저장은 실제 투자 기능이 없으므로 투자량0P로 이전할 수 있다. 최초 한 번만 포인트를 보정해 중복 지급을 막고 새 버전의 이전 완료 상태를 관리해야 한다. 파일을 불러올 때마다3P를 더하거나 기존 미사용P에 새 총량을 중복 가산하지 않는다.

돈·재료·스킬 보유/장착·설정 등 다른 영구 데이터를 보존한다. 현재 레벨 진행EXP를 새 경험치 테이블 기준으로 임의 환산하거나 Lv.5에서 버려진 EXP를 추정 복구하지 않는다. Lv.1~49의 다음 레벨 필요EXP는 성장1차 초기 테스트값 `100+50×(현재 레벨-1)`로 문서화했으며 Lv.1→50 총63,700EXP다(ProgressionSystem §3.3.1). 최종 튜닝·2층 이후는 미확정이며 표의 누적EXP를 기존 현재 레벨 진행EXP로 바꿔 저장하거나 보존 레벨을 역산하지 않는다. 최초1회 포인트 보정·완료 상태·영구 데이터 보존 원칙을 유지한다. 성장1차 이후 테스트 표 적용 및 v3 이전 보고는 §16을 따른다.

### 6.4 이전 전 원본·백업 보호와 새 버전

이전 전에 기존 주 저장 파일과 .bak을 **별도로 보호**해야 한다. 평소 .bak 교체만으로 이전 전 상태가 영구 보존된다고 간주하지 않는다. 현재 구현 보고는 .pre-v2/.pre-v3 아래 주 파일·백업을 SHA256별 별도 보호하며 덮어쓰기/자동 삭제하지 않는다. 이는 .bak 순환과 구분한다.

현재 CharacterSnapshot의 기본 버전은3이며 v1~v3 읽기·완료 상태 progressionV2Applied·세 투자 필드를 코드에서 확인했다. 정상 v1은 무투자 검증 후 Lv×3으로 한 번 보정하고 정상 v2는 기존P를 보존해 v3로 확장한다는 보고다. v3는 각 투자0~100 및 미사용P+세투자=레벨×3을 검증한다. 전체 후보 파일 저장 성공 후 live 세션에 복원하며 재로드 시 재지급하지 않는다. .tmp/.bak·체크섬·손상 원본 보호 구조는 유지한다.

### 6.5 이상 데이터·실패 복구와 구현 경계

이상 레벨/EXP·음수/과다 포인트·투자 상한/총량 오류·미지원 버전/필드는 현재 구현에서 LoadBlocked로 차단한다는 보고다. 의미 충돌을 오래된 백업으로 자동 덮지 않는 처리와 .tmp 쓰기 실패/백업 복구의 격리 검사 보고가 있다. 사용자 실데이터의 모든 비정상 조합·중단/강제 장애 경계는 전수 검증되지 않았다. 임의 clamp·포인트 삭제·레벨 변경·사용자 저장 초기화를 문서 승인만으로 실행하지 않는다.

v3 이전·투자 저장은 Codex 구현 보고와 이번 관련 코드 읽기 확인으로 구분한다. 사용자 원본 저장에 대한 파괴/강제 이전 테스트를 수행한 것으로 표현하지 않는다. 기존 레벨/투자 결과/영구 보유를 보존하는 원칙을 유지한다.

---

### 6.6 500G 초기화의 단일 저장과 메모리 확정

메인 로비에서 고정500G(초기 테스트값), 투자량>0·골드 충분 등 자격을 최종 확인한다. 기존 **v3 스냅샷과 저장 경로를 재사용**하며 새 스키마/저장 시스템을 추가하지 않는다. Capture 후보에서 money−500, 미사용P+세투자 합, 세투자0만 변경해 기존 Write로 함께 기록한다. 파일 쓰기 성공 후 골드와 성장 메모리를 함께 설치한 다음 알림을 보낸다. 실패는 원래 골드·투자·주파일/백업을 유지한다는 격리 검사 보고이며 재시도 시 중복 차감하지 않는다.

레벨·현재EXP·아이템·장비·보유/장착 스킬·재료·설정·정산ID 등 후보의 다른 영구 정보 및 런 보상 누계는 보존한다.100P 패시브 상태만 정리하고 일반 스킬 쿨타임·물약·부활은 유지한다. 예약·잔류 스킬은 실행 전 거부한다. 인라인 첫 클릭은 저장하지 않는다.

**읽기 전용 코드 확인:** CharacterSaveService의 CanResetStats/TryResetStats에서500G·무투자/권한 검사, 후보 Write 뒤 ApplyResetSnapshot/ApplyCommittedMoney 순서를 확인했다. 성공 후 알림 오류는 이미 저장된 후보를 재설치하며 재과금 가능한 쓰기 실패로 돌려보내지 않는다. 내부 HP 갱신 재시도마저 실패하면 LoadBlocked/재실행 안내를 사용하지만 해당 이중 실패 경로는 미주입이다. 이번 작업에서 실제 저장을 실행하거나 사용자 파일을 변경하지 않았다.

## 7. 던전 클리어 보상 저장

### 7.1 클리어 조건

보스를 처치하면 던전 클리어 상태가 확정된다.

### 7.2 클리어 보상 지급 시점

**최신 확정 규칙**

보스 사망 즉시 기존 클리어 보상을 확정·지급하고 저장한다. 실제 사망 효과 완료까지 기다리는 것은 결과창 시각 표시뿐이며 최초 화면 표시를 지급/저장 조건으로 삼지 않는다.

결과창의 열기·닫기 상태와 보상 지급 및 저장은 분리한다.

### 7.3 클리어 처리 관계

기획상 필요한 처리 관계는 다음과 같다.

1. 보스 처치
2. 던전 클리어 상태 확정
3. 클리어 보상 결정 및 지급
4. 지급한 보상 저장
5. 실제 보스 사망 효과 완료 통지 뒤 결과창에 확정된 보상 표시

이 과정은 보상과 결과창의 관계를 설명한 것이며, 실제 코드 내부의 상세 이벤트 순서를 확정하는 것은 아니다.

### 7.4 결과창 닫기

결과창을 닫아도 이미 지급된 클리어 보상은 유지한다.

닫기 동작을 저장 완료의 필수 조건으로 사용하지 않는다.

### 7.5 결과창 재열기

결과창을 다시 열면 해당 런의 기존 보상 데이터를 표시한다.

새로운 보상 지급 및 저장 처리를 반복하지 않는다.

### 7.6 로비 복귀

결과창에서 로비로 이동하더라도 클리어 보상은 유지한다.

로비 이동 버튼을 눌러야만 클리어 보상이 저장되는 구조에 의존하지 않는다.

### 7.7 게임 종료

클리어 보상이 지급 및 저장된 뒤 게임을 종료하더라도 보상이 유지되어야 한다.

### 7.8 중복 지급 방지

동일한 런의 클리어 보상이 반복 지급되지 않아야 한다.

중복 지급 가능성이 있는 상황:

- 결과창 최초 표시 과정의 중복 실행
- 결과창 닫기 및 재열기
- 로비 이동
- 저장 처리 재호출
- 이미 처리한 결과에 대한 재진입

실제 구현에서 지급 완료 상태를 관리하는 방식은 기존 코드를 확인한다.

## 8. 던전 실패와 데이터 유지

### 8.1 실패 조건

부활 가능 횟수 2회를 모두 사용한 뒤 최종 사망하면 던전 실패가 발생한다.

### 8.2 획득 보상 유지

**확정 규칙**

던전 실패 시에도 이미 획득한 보상은 100% 유지한다.

유지 대상:

- 돈
- 경험치
- 재료
- 이미 획득한 아이템

### 8.3 미획득 보상

아직 획득하지 않은 보스 보상과 클리어 전용 보상은 지급하지 않는다.

### 8.4 엘리트 보상

엘리트 몬스터가 존재하고 이미 처치 보상을 지급받았다면 실패 시 해당 보상을 임의로 회수하지 않는다.

### 8.5 실패 결과창

실패 결과창은 실제로 획득한 보상을 표시한다.

결과창을 표시하거나 닫는 이유로 이미 획득한 보상을 회수하지 않는다.

### 8.6 저장 확인

던전 실패 및 로비 복귀 이후에도 기존 획득 보상이 유지되는지 확인한다.

경험치 획득으로 인한 레벨 상승 및 성장 결과도 영구 데이터로 유지한다.

## 9. 방 이동과 데이터 유지

### 9.1 방 이동

플레이어가 한 던전 내에서 다음 방으로 진행하면 런 데이터가 유지되어야 한다.

### 9.2 유지 대상

- 현재 체력
- 남은 물약
- 남은 부활 횟수
- 획득한 돈
- 획득한 경험치
- 획득한 아이템
- 획득한 재료
- 전투 기록

### 9.3 방 교체 시 주의사항

방이 교체된다는 이유로 플레이어의 영구 성장 데이터나 획득한 보상을 초기화하지 않는다.

이전 방의 공격 오브젝트를 정리하는 과정과 플레이어의 보유 데이터 관리는 구분한다.

### 9.4 게임 종료 시 런 복원

현재 진행 중인 방, 체력, 물약, 부활 횟수 등을 게임 종료 후 복원하는지 여부는 미확정이다.

새로운 중단·재개 기능을 임의로 추가하지 않는다.

## 10. 던전 다시 시작

### 10.1 기본 동작

결과창에서 다시 시작하면 동일한 층과 난이도로 새로운 런을 시작한다.

### 10.2 초기화 대상

확정된 초기화 규칙:

- 첫 번째 방부터 시작
- 플레이어 체력 초기화
- 물약 수량 3개
- 부활 가능 횟수 2회

### 10.3 유지 대상

새 런을 시작하더라도 다음 영구 정보는 유지한다.

- 돈
- 경험치
- 레벨
- 보유 아이템 및 재료
- 장비
- 스킬
- 영구 성장 데이터

### 10.4 런 기록

새로운 런은 이전 런의 결과를 그대로 재사용하지 않아야 한다.

해당 런의 전투 기록과 보상 기록은 새로운 플레이 단위로 관리한다.

단, 결과창을 닫았다가 다시 여는 것은 새로운 런이 아니다.

### 10.5 중복 보상

새 런 시작 과정에서 이전 런의 클리어 보상을 다시 지급하지 않아야 한다.

---

## 11. 로비 복귀

### 11.1 결과창에서 로비 복귀

결과창의 로비 이동 버튼을 통해 메인 로비로 복귀한다.

이미 획득하고 저장한 보상은 유지한다.

### 11.2 퍼즈 메뉴에서 로비 복귀

퍼즈 메뉴에서 로비로 이동하더라도 이미 획득한 보상은 유지되어야 한다.

### 11.3 중도 종료

클리어 또는 실패가 확정되기 전에 자발적으로 던전을 종료하는 경우의 전체 처리 규칙은 현재 자료에서 확정되지 않았다.

특히 다음 사항은 추가 확인이 필요하다.

- 진행 중인 런을 다시 이어서 플레이할 수 있는지
- 중도 종료 시 던전 진행 상태를 저장하는지
- 결과창을 표시하는지
- 전투 기록을 유지하는지

이미 획득한 보상을 유지한다는 확정 규칙과 중도 종료의 세부 흐름은 구분한다.

## 12. 저장 및 불러오기 처리

### 12.1 저장 기능

영구 보유 데이터를 저장하여 게임 종료 후에도 유지한다.

### 12.2 불러오기 기능

기존 저장 데이터가 존재하는 경우 해당 데이터를 불러와 플레이어의 영구 보유 상태에 반영한다.

### 12.3 저장 대상 일치

저장된 데이터와 게임 내부 상태, HUD 및 인벤토리 표시가 일치해야 한다.

### 12.4 중복 초기화 방지

씬 변경이나 UI 재생성 과정에서 저장된 영구 데이터가 기본값으로 덮어써지지 않도록 확인한다.

### 12.5 현재 저장 구조와 기존 이전 이력

WORK_STATUS의 과거v1 저장 보고와 개편 전 읽기 전용 조사는 당시 기록으로 보존한다(§6.2/16). 현재v3는 투자3종과 완료 상태를 저장하고 정상v1/v2를 이전한다. 체크섬·.tmp 쓰기/교체·.bak 복구와 이전 전 별도 보호는 유지한다(§6.4).

500G 초기화는 이미 구현된v3 전체 후보 저장을 재사용한다(§6.6). 새 저장 버전/외부 서비스를 추가하는 기획이 아니다. 저장 슬롯·강제 장애 등 미명시 정책을 임의 확정하지 않으며 구현 보고와 직접 실행 검증을 구분한다.

---

### 12.6 타이틀 진입과 기존 영구 데이터 보존

OREPLUME의타이틀 게임 시작은 기존 영구 저장을 기존 불러오기/복원 경로로 읽고 로비로 진입한다. 최초 실행만 기존 정상 초기화 규칙을 쓰며 타이틀 재진입/버튼 선택만으로 기존 캐릭터·재화·재료·장착/보유스킬·성장·설정을 초기화하지 않는다. 기존백업/체크섬/실패 복구/중복초기화 방지를 유지한다. 새 스키마/저장경로 변경·새게임/이어하기 UI·중단런 복원을 추가하지 않는다. 실제 시작씬/초기화 연결·타이틀 Unity완료는 미확인이다.

28일사망결과 순서 보고의 정산ID/체크섬·표시 전후 저장불변/추가 지급0은 기존Codex 검사이며 이번 실제저장/코드/Play 확인이 아니다. 사망 시 보상 선처리와 화면대기를 분리하되 기존 저장실패/재시도·미정산 복구·중복 정산 방지 규칙은 바꾸지 않는다. 상세는 [BossSystem](BossSystem.md) §9.6이다.

## 13. 개발용 저장 초기화

### 13.1 목적

개발 및 테스트 과정에서 저장된 플레이어 데이터를 초기화하여 초기 상태부터 기능을 검증하기 위한 도구이다.

### 13.2 현재 상태

사용자는 테스트를 위한 저장 기록 삭제 단축키 또는 기능의 필요성을 요청한 이력이 있다.

정확한 단축키와 구현 여부는 확인되지 않았다.

### 13.3 초기화 시 고려 사항

기존 인수인계에 기록된 요구 및 주의사항:

- 개발용 기능임을 명확히 표시
- 실수로 초기화하지 않도록 확인 절차 제공
- 저장 파일과 현재 메모리 상태의 관계 고려
- 자동 저장으로 이전 데이터가 즉시 다시 생성되지 않도록 처리
- 초기화 대상 범위 표시
- 무관한 다른 프로그램의 데이터 삭제 금지

### 13.4 미확정 사항

- 초기화 입력키
- 초기화 기능의 UI 제공 여부
- 초기화할 데이터 범위
- 초기화 후 씬 또는 게임 상태
- 기능을 사용할 수 있는 개발 환경

기존 프로젝트를 확인하기 전까지 새 단축키를 지정하지 않는다.

## 14. 데이터 불일치 및 중복 처리 방지

### 14.1 기본 원칙

저장 및 불러오기 과정에서 플레이어 보유 데이터가 의도치 않게 증가하거나 감소하지 않아야 한다.

### 14.2 경험치

- 몬스터 처치 시 경험치 지급
- 결과창에서는 이미 지급한 경험치 표시
- 결과창 재열기 시 경험치 재지급 금지
- 저장 데이터 복원 시 경험치 중복 적용 방지

### 14.3 아이템

- 획득한 아이템을 인벤토리에 반영
- 저장 및 복원 후 보유 수량 유지
- 결과창 재열기 시 아이템 재지급 방지

### 14.4 장비

- 보유 장비와 장착 상태 일치
- 제작 결과 중복 지급 방지

## 16. 현재 구현 현황

**2026-10-23 최신 사용자 승인 반영.** 승인 기획과 [WORK_STATUS.md](../WORK_STATUS.md)의 Codex 구현·검증 보고를 구분한다. 이번 작업은 문서 갱신과 관련 코드의 읽기 전용 확인이며 Unity 컴파일·Play·빌드 검증은 재실행하지 않았다. 아래 과거 구현 기록은 당시 이력으로 보존한다.

> **문서 갱신: 2026-10-21 / 승인 기획 v0.1 유지.** 구현 현황은 [WORK_STATUS.md](../WORK_STATUS.md)의 Codex 보고와 그 안에 기록된 Unity MCP 테스트(최종 기록일 2026-10-20)를 대조한 것이다. 이번 문서 작업에서 Unity 코드·씬·프리팹을 검사하거나 컴파일·플레이 테스트를 재실행하지 않았다. 아래의 ‘통과’·‘확인’은 당시 기록의 주장이다. 임시값은 최종 밸런스가 아니며 본문의 미확정 기획을 새로 확정하지 않는다. 기존 인수인계 및 확인 필요 목록은 보존하되 구현 사실의 근거와 시점은 최신 보충을 우선한다.

### 2026-10-21 구현 기록 대조

**Codex 구현 완료 보고:** 기존 DungeonRunManager에 CharacterSaveService를 연결하고 CharacterSaveFile v1 JSON payload와 SHA256 체크섬을 사용한다. 임시 파일 Flush(true) 후 원본 교체, 정상 .bak 백업, 손상 주 파일 .corrupt-GUID 보존 후 백업 복구 방식이다.

- 주 파일/백업 모두 로드 실패 시 LoadBlocked로 자동 저장과 명시적 Flush를 차단한다. 일반 저장 실패는 오류 안내와 재시도를 제공하며 귀환·종료 및 결과의 귀환/재시작을 차단한다. 모든 일시적 쓰기 오류가 곧 LoadBlocked라는 의미로 확대하지 않는다.
- 저장 대상: 레벨·현재 경험치·미사용 스탯 포인트·돈·재료 수량/등록순서·보유 스킬 ID·E/R 장착·카메라 흔들림 배율. 알 수 없는 재료/스킬 ID는 경고와 함께 별도 보존한다. 전용 재료 추가 후 5종 카탈로그를 연결한 기록이다.
- 영구 변경 후 0.4초 unscaled 디바운스 자동 저장, 처치 보상 트랜잭션 중간 Flush 차단, 입장·귀환·종료 전 Flush와 정상 종료 마지막 시도를 사용한다.
- 결과 정산은 lastSettledPlayId와 보유 데이터를 같은 스냅샷으로 즉시 저장하며, 저장 실패 시 메모리 보상을 유지하고 재시도에 재추첨/재지급하지 않는다.
- 실제 장비 제작·분배 스탯은 당시 미구현으로 그 결과 데이터도 저장 대상에 없다. 진행 중 던전의 방·적·체력·물약·생명·쿨타임·UI를 저장하지 않고 중간 이어하기를 지원하지 않는 구현 기록이다. 승인된 미래 장비/성장 저장 방향을 삭제한 것이 아니다.

**당시 저장 경로:** 빌드는 `C:/Users/User/AppData/LocalLow/DefaultCompany/mineDungeon/character.json`, Editor는 같은 폴더 아래 `Editor/character.json`으로 분리한다. 이는 기록상의 경로이며 이번 작업에서 사용자 저장 파일에 접근하거나 초기화하지 않았다.

**개발용 초기화 구현 보고:** Play Mode의 Ctrl+Shift+F9 또는 Tools/Mine Dungeon/개발용/플레이어 진행 데이터 초기화 메뉴와 native 확인창을 사용한다. Editor/UNITY_EDITOR 전용이다. 저장·보상 트랜잭션·씬 재시작 중에는 거부하고 주 파일/.bak을 신규 스냅샷으로 교체한 뒤 메모리 성장/인벤토리/정산 ID와 런을 정리해 Main으로 돌아간다. 실패 시 LoadBlocked 및 재시도를 사용한다. 카메라 흔들림 설정과 무관한 데이터는 보존한다. 테스트 기본 스킬 4종은 확정 초기 지급으로 승인하지 않는다.

**기록된 Unity MCP 테스트:** 저장 17항목 + 별도 Play 재실행 5항목, 재연결 후 입력/unknown ID 8항목 및 선택 필드 누락 로드 검증을 구분한다. 손상 주 파일/정상 백업 복구와 둘 다 손상 시 쓰기 차단, 성장/보유/장착/설정 복원, 결과 정산 ID·재시도 중복 무지급, 재료 5종 저장 복원이 보고됐다. 개발 초기화는 격리 경로의 메서드 호출로 기본값·설정 유지·주/백업 일치·재진입·반복 초기화·실패/재시도를 확인한 기록이며 물리 단축키/native 확인창 클릭·ESC 자동 검증은 하지 않았다.

## 19. 문서 관리

본 문서는 광산던전의 영구 데이터 저장, 불러오기, 런 상태와 영구 데이터의 구분 및 보상 중복 지급 방지 규칙을 관리한다.

관련 기준 문서는 다음과 같다.

- `DungeonSystem.md`: 던전 진행, 클리어·실패·재시작
- `RewardSystem.md`: 보상 획득과 지급 시점
- `ProgressionSystem.md`: 경험치, 레벨, 스탯 성장
- `EquipmentSkillSystem.md`: 장비, 스킬, 제작
- `PlayerSystem.md`: 체력, 물약 및 부활
- `UISystem.md`: 결과창, HUD, 인벤토리

저장 관련 기획을 변경할 때는 획득 보상, 성장, 장비 및 던전 진행 시스템에 미치는 영향을 먼저 검토한다.

사용자 승인 후 공식 문서 수정안을 작성하고 관련 변경 내역을 `CHANGELOG.md`에 기록한다.

실제 구현 작업에서는 기존 저장 구조를 먼저 확인하고, 저장 데이터를 임의로 삭제하거나 새로운 형식으로 교체하지 않는다.
